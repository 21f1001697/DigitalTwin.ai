01Executive Summary

Executive Summary

Product Overview

DigitalTwin.ai is a live software model of a vehicle assembly line for plant teams who can see a station's output today but not its strain. It fuses three tiers of signal — direct PLC/MES telemetry, camera-based vision inference, and manual-checklist data — into one station-health model, then runs a forward propagation simulation so that a forming bottleneck or an emerging defect is forecast minutes before it becomes a missed shift target or a batch of exposed vehicles.

Vision Statement

"No station on the line is invisible, and no defect travels twenty vehicles before someone notices — regardless of how that station was instrumented a decade ago."

Mission Statement

DigitalTwin.ai's mission is to make predictive visibility available to the 60–70% of stations on a typical mixed-model line that were never wired for it, without requiring a capital retrofit project or a pause in production to get there.

02Problem Analysis

Problem Analysis

Existing Market Gaps

ApproachWhat It Misses
MES / line-balancing dashboardsReport throughput and downtime after the fact; no forward propagation model, no per-vehicle defect-exposure forecast
Full digital-twin platforms (Siemens, Dassault)Model geometry and PLC signals in exhaustive detail — assume a fully instrumented line, and take 12–18 months to stand up
End-of-line vision inspectionCatches a defect after assembly is complete, when rework is most expensive — not upstream, where it started
CMMS (SAP PM, Maximo)Workflow and scheduling only; zero condition-monitoring intelligence about what is actually degrading
OEM telematics / andon systemsDepend on an operator noticing and reporting a subtle motion or timing change in real time, under production pressure

User Pain Points

  • Delayed bottleneck discovery — a station running 8–10% slow shows up as a full buffer, then a starved downstream station, then a missed shift target, by which point the cause is minutes upstream and untraceable in the moment
  • Delayed defect discovery — a subtle process deviation surfaces only at final inspection, by which time 20–40 vehicles may carry the same undetected issue
  • Uneven visibility — 60–70% of stations on a real mixed-model line carry little or no direct telemetry, so most of the line is a blind spot today
  • No trust mechanism — existing "AI monitoring" tools that cry wolf erode floor-level trust faster than they build it, and most offer no way to see their own track record

Every existing option assumes either a fully instrumented line (enterprise twins) or accepts total blindness at uninstrumented stations (MES/CMMS). Nobody fuses partial instrumentation with vision to cover the gap, then forecasts forward from whatever signal is actually available.

04Product Objectives

Product Objectives

Short-Term Goals (Prototype & Pilot)

  • Demonstrate the SEE→MODEL→PREDICT→ACT pipeline on a simulated 30–50 station line with realistic Tier A/B/C sensor coverage
  • Validate that the same degradation severity is detected with high confidence at instrumented stations and honestly flagged as low-confidence at manual-checklist stations
  • Deploy read-only on one real pilot line without any PLC/control-system modification

05Features and Functional Requirements

Features and Functional Requirements

MUST MVP-blocking   SHOULD High value   COULD Nice to have   WON'T v1 Deferred

F-01 · Station Tier Registry

MUST

Description: Every station is registered with its position in the line graph, upstream/downstream buffer capacities, takt target, and a sensing tier — Tier A · Instrumented Tier B · Vision Tier C · Manual. This tag drives which pipeline and confidence model applies.

User story: As an industrial engineer, I want to register each station's sensing tier so the twin knows how much to trust its own read at that station.

Acceptance criteria: Station created with tier, buffer capacity, and takt target; tier is editable as instrumentation changes; tier is visible on every downstream view of that station.

Dependencies: None.

F-02 · Telemetry & Vision Ingestion

MUST

Description: Tier A stations stream PLC/MES events (cycle time, fault codes, process parameters) via a read-only event-bus subscription. Tier B stations run the optical-flow pipeline (reused from the Round 1 prototype) on a fixed camera feed to reconstruct cycle time and motion-anomaly signals. Tier C stations contribute checklist pass/fail data at inspection cadence.

User story: As a plant IT lead, I want the twin to ingest existing data streams without any write access to control systems, so there is zero operational risk to live production.

Acceptance criteria: Ingestion is strictly read-only; a dropped camera or feed marks the station "unmonitored," never silently frozen on stale data.

Dependencies: F-01.

F-03 · Per-Station Anomaly Detection

MUST

Description: An Isolation Forest fitted per station on its own historical "healthy" window scores incoming features unsupervised — no labelled fault data required. Each station is judged against its own baseline, never a factory-wide norm.

User story: As a quality engineer, I want each station's anomaly threshold to reflect that station's own normal operating range, so a naturally slower station doesn't generate constant false alarms.

Acceptance criteria: Model retrains on a rolling healthy window; anomaly score is bounded 0–1; flags require sustained deviation over a rolling tail window, not a single noisy sample.

Dependencies: F-02.

F-04 · Confidence-Banded Output

MUST

Description: Every anomaly score and prediction is paired with a confidence value derived from the source station's tier (and, for Tier B, live signal quality — lighting, occlusion, angle). Low-confidence output is visually and textually distinct everywhere it appears.

User story: As a floor supervisor, I want to immediately tell whether a flag is PLC-certain or vision/manual-inferred, so I calibrate my response accordingly.

Acceptance criteria: No screen displays a score without its confidence label; Tier C/low-confidence Tier B flags never render with the same visual weight as Tier A.

Dependencies: F-01, F-03.

F-05 · Downstream Propagation Forecast

MUST

Description: On a sustained anomaly, a discrete-event simulation propagates the disruption through the line graph — buffer fill/drain dynamics, takt mismatches — forecasting which stations will bottleneck, when, and which in-progress vehicles (by position/VIN) are exposed.

User story: As a floor supervisor, I want to know not just that a station is degrading, but which station and how many vehicles will be affected, and when.

Acceptance criteria: Forecast returns at least the next downstream station, a time-to-impact estimate, and an exposed vehicle range when the degradation is defect-like.

Dependencies: F-01, F-03.

F-06 · Explainable Recommendation Queue

MUST

Description: Every flagged event resolves to one ranked, plain-language recommendation (inspect, reassign labour, hold buffer, targeted re-inspection) rather than a bare anomaly score, always requiring human approval.

User story: As a floor supervisor, I want one clear next action, not a wall of alerts, so I'm not left interpreting a raw number under production pressure.

Acceptance criteria: No autonomous action is ever taken; every recommendation has an Approve/Dismiss control and a logged rationale.

Dependencies: F-04, F-05.

F-07 · Live Line Map

MUST

Description: A single visual rendering of every station — colour-coded by health, tagged by tier, showing buffer occupancy between stations.

Dependencies: F-01 through F-04.

F-08 · Outcome Logging & Accuracy Audit Trail

MUST

Description: Every prediction is logged against its eventual real-world outcome, building the accuracy and savings record leadership uses to approve rollout.

User story: As a leadership sponsor, I want an audited accuracy history, not a one-time accuracy claim, before I approve expansion spend.

Dependencies: F-05, F-06.

F-09 · Weekly Trend & Plant Rollup View

SHOULD

Description: Plant-manager-facing view: recurring at-risk stations across the week, prediction accuracy trend, OEE impact.

Dependencies: F-08.

F-10 · Instrumentation Shortlist Generator

SHOULD

Description: Ranks stations by how much their sensing-tier uncertainty limits overall twin accuracy, so scarce maintenance-window retrofit budget targets the highest-value stations first.

Dependencies: F-04, F-08.

F-11 · Vision Upgrade Deployment (Tier C → B)

SHOULD

Description: Self-contained camera install at a Tier C station with a usable sightline, upgrading it to Tier B without touching PLC logic or requiring a maintenance window.

Dependencies: F-01, F-02.

F-12 · Leadership Business-Case Dashboard

COULD

Description: Quarterly view translating F-08's audit trail into downtime hours avoided, defect batches caught early, and ROI against instrumentation spend.

F-13 · Multi-Site Topology Support

WON'T v1

Description: Extending the graph and simulation beyond a single line to a full plant, then multiple plants with differing layouts — targeted for the Scale phase once the single-line business case is proven.

06User Flow and Journey

User Flow and Journey

Core Detection-to-Action Flow

Station ST14 (Tier C · manual) cycle time drifts +22% ↓ anomaly scorer flags ST14, confidence: LOW (vision/manual-inferred) ↓ propagation sim: buffer before ST17 will empty in ~6 cycles ↓ forecast: ST17–ST19 will run starved within ~4 minutes ↓ exposure check: VINs #4033–#4040 built during drift window flagged ↓ supervisor console surfaces: "Schedule inspection of ST14 this shift" [Approve] [Dismiss] ↓ supervisor approves → action + outcome logged, line map updates live

Onboarding Flow (New Plant/Line)

Register line topology and station tiers (F-01) → connect read-only MES/SCADA feed for Tier A stations → install cameras at feasible Tier B stations → twin begins learning per-station healthy baselines → first live recommendations surface once baseline history is sufficient (target: within one week).

Navigation / Information Architecture

  • /twin — Live line map (default supervisor view)
  • /twin/station/[id] — Station detail: tier, confidence, health history, recent flags
  • /vehicles/[vin] — Per-vehicle exposure trace across all stations it passed through
  • /actions — Recommendation queue, pending and historical, with approval log
  • /trends — Plant manager weekly rollup
  • /business-case — Leadership audit trail and ROI dashboard
07UI/UX Requirements

UI/UX Requirements

Design Principles

  • The floor, abstracted, not decorated — the line map reads like the physical layout a supervisor already walks
  • Sensing tier and confidence are never hidden — a Tier A read and a Tier C read must look visually distinct everywhere, not just on hover
  • Forecast vs. present tense, visually separated — a predicted future bottleneck must never look identical to a current one
  • One action at a time — the recommendation queue surfaces the single highest-priority action, not a wall of alerts

Accessibility Requirements

RequirementStandard
Colour contrastWCAG 2.1 AA; severity and tier are never colour-only, always paired with an icon and text label
Keyboard navigationAll interactive elements reachable by keyboard; visible focus ring
Screen readerLine-map and charts carry ARIA text summaries; confidence bands are announced, not just shown visually

Responsive Behaviour

Desktop-first for the floor supervisor and plant manager views (control-room and office displays); a simplified mobile view for the recommendation queue and Approve/Dismiss actions only, so a supervisor can act from the floor without needing the full line map on a phone screen.

Recommended Screens

  • Live Line Map, Station Detail, Vehicle Exposure Trace, Action Queue, Weekly Trend Rollup, Leadership Business-Case Dashboard, Instrumentation Shortlist
08Technical Requirements

Technical Requirements

Suggested Architecture

LAYER 1 — SENSING PLC/MES read-only feed | Fixture-mounted cameras | Checklist entry LAYER 2 — INGEST Event bus, station- and tier-tagged LAYER 3 — INFERENCE Optical-flow feature extraction (Tier B) | Isolation Forest per station | Confidence model LAYER 4 — TWIN CORE Line graph model | Discrete-event propagation simulator LAYER 5 — ACTION Ranked recommendation engine | Human approval gate | Outcome logger LAYER 6 — PRESENTATION Live line map | Station/vehicle detail | Trend & business-case dashboards

APIs Needed

APIPurpose
MES/SCADA read connectorSubscribe to existing Tier A telemetry without any write path back into control logic
Vision ingestion serviceReceive camera feeds, run optical-flow feature extraction at the edge, forward only extracted features upstream (not raw video)
Twin query APIServe line map, station detail, and recommendation data to the frontend
Outcome-logging APIRecord actual outcomes against prior predictions for the audit trail
Notification/alerting APIPush recommendation cards to supervisor consoles and mobile

Database Considerations

  • Time-series store for per-station feature streams and anomaly scores (high write volume, append-only)
  • Relational store for line topology, station tiers, buffer configuration, and the recommendation/approval log
  • Outcome-log table designed for audit queries (prediction vs. actual) from day one, not bolted on later

Security Requirements

  • Strictly read-only integration with PLC/MES/SCADA — no write path exists at the architecture level, not just by policy
  • Cameras are an independent, non-networked sensing layer with no connection back into control systems
  • Role-based access separating floor supervisor, quality engineer, plant manager, and leadership views
  • Raw video processed at the edge; only extracted features and short flagged-cycle clips (if retained) leave the local network

Scalability Considerations

  • Station-tier model is layout-agnostic by construction, so scaling to a new line/site is a configuration exercise, not a re-architecture
  • Edge inference for vision keeps bandwidth flat as camera count grows
  • Propagation simulator scoped per line at MVP; multi-line/plant graph support is an explicit Phase 4 item (F-13), not assumed from day one
09AI / Automation Requirements

AI / Automation Requirements

AI Use Cases

Use CaseApproachOutput
Vision cycle-time & motion-anomaly inferenceFarneback optical flow → per-cycle feature vector (duration, magnitude profile, directional consistency)Inferred cycle time + motion-anomaly score per station cycle
Per-station anomaly detectionIsolation Forest, trained per station on its own operating historyAnomaly score (0–1), station-specific

Model Suggestions

MVP: Isolation Forest per station — unsupervised, so it needs no labelled fault data at launch and solves the cold-start problem inherent to every new deployment. Phase 2+: once outcome-logged data (F-08) accumulates, a supervised model (e.g., a temporal convolutional network) can be layered in to name specific fault types rather than a generic anomaly, evaluated against the unsupervised baseline before replacing it.

Training/Data Needs

  • MVP requires no labelled fault data — each station's own "healthy" history is sufficient to fit its baseline
  • Outcome logging (F-08) is the mechanism that eventually produces the labelled data a supervised upgrade would need
  • Vision pipeline validation requires ground-truth cycle-time comparison against at least one real Tier A station before any Tier B deployment is trusted

Ethical Considerations

  • Human in the loop, always — the twin never autonomously halts a line, adjusts control logic, or clears a vehicle
  • No silent guessing — a station with degraded or missing signal is marked "unmonitored" or low-confidence, never defaulted to "healthy"
  • Camera scope — cameras are positioned on stations/fixtures, not tracking individual operators; only motion features are retained, not identity
  • Model transparency — every recommendation names its contributing signals, so floor staff can apply their own judgement rather than blindly trust or dismiss the output

15Deployment Strategy

Deployment Strategy

CI/CD: standard staged pipeline (unit → integration → staging replay against recorded line data → production) for the twin core and dashboards; vision-model updates additionally validated against the ground-truth benchmark station before rollout. Hosting: edge inference for vision (on-prem or plant-local compute, to avoid streaming raw video off the floor) with the twin core, dashboards, and outcome log hosted in cloud SaaS. Rollback: a new model version runs in shadow mode alongside the current one until its predictions are validated against the outcome log, before it is promoted to drive live recommendations.

16Future Enhancements

Future Enhancements

  • Cross-line and whole-plant topology (F-13) — propagation modelling across line-to-line buffers and shared sub-assembly feeds
  • Supervised fault classification — once outcome-logged data is sufficient, move from generic anomaly to named defect-type prediction per VIN
  • Maintenance correlation — link recurring vision-flagged motion anomalies to upcoming equipment wear, feeding predictive maintenance scheduling
  • CMMS/ERP integration — auto-raise work orders in existing SAP PM/Maximo systems from approved recommendations
  • Operator-fatigue-aware baselines — shift-position-aware normal ranges, since a station's "normal" motion pattern legitimately shifts across an 8-hour shift
17Final Recommendations

Final Recommendations

Go-to-Market Suggestions

Lead with the read-only, no-maintenance-window deployment story — it is the single biggest lever against the 6–12 month enterprise sales cycle risk, since it removes the control-system change request that normally gates a pilot. Offer a scoped, time-boxed pilot on one line with an explicit outcome-logging commitment, so the audited accuracy record (F-08) becomes the sales asset for expansion, not a marketing claim.

Growth Strategy

Land on one line, prove the business case with real outcome-logged data, then expand within the same plant before pursuing a second site — each expansion is justified by the previous site's audit trail rather than a fresh pitch. The instrumentation shortlist (F-10) doubles as a natural expansion mechanism: as a plant sees value, it invests its own scarce maintenance-window budget in the stations the twin itself has identified as highest-value.

Product Positioning

DigitalTwin.ai is not a competitor to full physics-accurate digital-twin platforms, nor to end-of-line vision inspection, nor to CMMS — it is the layer that is missing between them: multi-tier sensing fused with forward prediction, built for the line as it actually is, not the line an enterprise twin assumes it should be.
