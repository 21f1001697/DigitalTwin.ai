1Problem Framing

The gap Round 1 named — and what Round 2 adds

In Round 1 we argued that a single slow or degrading station on an assembly line rarely announces itself — it shows up as an upstream queue, a starved downstream station, or a defect that isn't caught until dozens of vehicles later. Round 2's brief sharpens that problem with a fact every real plant already knows: the line is never uniformly instrumented. A 30–50 station mixed-model line is a patchwork built up over a decade or more — some stations wired into the MES with PLC-level telemetry, others running on a laminated checklist and an operator's judgment.

That patchwork changes what a "digital twin" has to be. It cannot assume a fully sensored ideal factory, because that factory doesn't exist. It has to be honest about which parts of its own picture are measured and which are inferred — and it has to keep working, safely, around live production it is not allowed to touch except in a handful of scheduled maintenance windows a year.

Compounding factors from the Round 2 brief

Real-world complexityWhy it defeats a naive twin
Uneven sensor coverageA model trained to expect PLC-quality data everywhere breaks silently at the manual-checklist stations — exactly where problems are least visible today
Multi-causal, intermittent root causesEquipment wear, operator variation, upstream part quality and environment rarely act alone; a single-signal anomaly flag can't separate them
No live retrofit accessNew sensors can only go in during scheduled maintenance windows — the twin must earn its value with the instrumentation already on the floor
Delayed defect surfacingA defect from Station 8 may only be caught at Station 41 — by which point the true exposure window has to be reconstructed after the fact
Stakeholder-specific viewsA floor supervisor, a plant manager and a leadership sponsor are reading the same twin for three different decisions on three different clocks
Multi-site generalisationLayout, equipment vintage and sensor maturity all vary site to site — a model tuned to one line's quirks won't transfer
Trust decays with false alarmsA prediction that doesn't materialise costs more than a missed one, because floor staff stop watching the ones that follow

The problem isn't just "predict bottlenecks and defects." It's predict them credibly, at a station you may not be able to fully see, without ever having touched the line to get there.

2Solution Design

SEE → MODEL → PREDICT → ACT, rebuilt for uneven instrumentation

2.1 Modelling approach — what's explicit vs. inferred

We model every station along the same four attributes regardless of instrumentation level — cycle time, throughput, defect signature, and confidence — but the source of each attribute differs by station tier:

Station tierWhat's measured directlyWhat's inferred
Tier A — Instrumented (PLC/MES telemetry: torque, vibration, temperature)Cycle time, process parameters, fault codesNothing — signals are used as-is with calibrated confidence near 1.0
Tier B — Vision-augmented (a camera reused from Round 1's core mechanism)Cycle time, motion/hesitation, rework loops via optical flowTorque/temperature proxies, correlated against any nearby Tier A stations of the same type
Tier C — Manual-checklist only (no sensor, no camera line-of-sight)Pass/fail and operator notes at checklist cadenceCycle time and health, inferred from upstream/downstream buffer behaviour and historical variance for that station

Every inferred value carries an explicit confidence score. A Tier C station's prediction is never displayed with the same visual certainty as a Tier A one — this is a hard UI rule, not a styling choice, because it's the single biggest lever against false-alarm-driven trust erosion.

2.2 Predictive techniques — matched to what data actually supports

  • Statistical process control (SPC) at Tier A/B stations with enough history — cheap, interpretable, and a good first filter before anything model-based runs
  • Unsupervised anomaly detection (Isolation Forest, carried over from the Round 1 prototype) for stations with no labelled fault data — learns each station's own "normal" rather than assuming one factory-wide baseline
  • Physics-informed constraints on the line-graph simulation (conservation of flow through buffers, monotonic cycle-time bounds) so the propagation model can't output a physically impossible forecast even when a station's inputs are noisy
  • Validation before trust: every model is back-tested on held-out historical windows before it's allowed to surface a live recommendation, and every live prediction is logged against its eventual outcome — this outcome log is what Section 4's accuracy claims are built on, and what keeps the model honest over time

2.3 Handling data gaps at Tier C stations

Three layers, in order of cost:

  1. Free — inference from neighbours. A Tier C station's buffer behaviour (how fast cars queue before it, how fast they clear after) already carries a signal about its own cycle time, without touching the station itself.
  2. Low-cost — a camera, not a sensor. Where there's a usable sightline, the same optical-flow pipeline from Round 1 upgrades a Tier C station to Tier B without any PLC integration or production downtime — install happens on a live line, no maintenance window required.
  3. Scheduled — targeted retrofit. For stations where neither of the above is viable, we produce a ranked "instrumentation shortlist" — the stations whose uncertainty most limits the twin's overall accuracy — so a plant's limited maintenance-window budget for physical retrofits is spent where it moves the needle most, not spread evenly.

2.4 Integration approach — around the line, not into it

The twin is strictly read-only with respect to production systems. It subscribes to existing MES/SCADA event streams and OT data feeds already flowing for other purposes (quality systems, historian databases), and adds cameras as an independent, non-networked sensing layer with no connection back into PLC logic. No control-system change, no PLC reprogramming, and no requirement for a maintenance window to deploy the core twin — maintenance windows are reserved solely for the optional physical retrofit step in 2.3.

2.5 From detection to action

Every flagged deviation resolves to one explainable statement, not a bare score: "Station 14 is degrading → Station 17 may be affected in 4 minutes → 9 vehicles are potentially exposed." A ranked recommendation follows — inspect, reassign, hold buffer — and a human always approves it. The twin never adjusts line speed, halts a station, or clears a vehicle on its own.

3Target Users

Three views, one underlying model

The same twin serves three audiences with fundamentally different decision cadences — so the product is one shared data model surfaced through three distinct views, not three separate tools.

Floor SupervisorReal time · seconds to minutes

Needs the live line map, right now: which station is straining, what's predicted downstream, one ranked action to approve. Success is measured in minutes saved before a bottleneck becomes a missed shift target.

Plant ManagerPlanning · daily / weekly

Needs trend views across the week: which stations recur as risk sources, how prediction accuracy is tracking, where labour or maintenance should be pre-positioned for the coming shifts. Success is fewer surprises at the weekly review.

Leadership SponsorInvestment · quarterly

Needs the business case: downtime hours avoided, defect batches caught early, cost of the instrumentation shortlist versus cost of the status quo, and a rollout path to the next line or site. Success is a fundable, de-risked expansion decision.

4Business Case & Impact

Where the value actually comes from

20–40
vehicles typically built between a defect-causing event and its discovery at final test — the exposure window this twin shrinks
2–3
cycle times of early warning the propagation model targets, before a bottleneck trips the shift's line rate
60–70%
of a typical mixed-model line's stations that carry little or no direct telemetry today — the segment this twin is built to cover

Where savings accrue

  • Reduced defect-exposure batches — catching a deviation within a handful of vehicles instead of dozens directly cuts rework and warranty cost per incident
  • Reduced unplanned downtime — earlier bottleneck warning converts emergency line stops into planned, lower-cost interventions
  • Better-targeted capital spend — the ranked instrumentation shortlist (2.3) means retrofit budget goes to the highest-uncertainty stations first, not spread thin
  • No integration capex or downtime — read-only deployment means value starts accruing before any maintenance window is spent

Path to proof

Because every prediction is logged against its eventual outcome (2.2), the business case is not a one-time estimate — it compounds into an audited accuracy and savings record that leadership can point to when approving expansion to the next line.

5Phased Roadmap

One line first, proven before it spreads

Phase 1 · Weeks 1–8
Prove the mechanism

Working prototype on simulated 30–50 station line with synthetic Tier A/B/C coverage. Validate the SEE→PREDICT pipeline and confidence-banded output against known injected-fault scenarios.

Phase 2 · Weeks 9–20
Pilot on one real line

Read-only integration with one plant's live MES/OT feeds plus targeted camera install at select Tier C stations. Outcome-logging begins; floor supervisor view goes live.

Phase 3 · Months 6–12
Prove the business case

Accumulate enough outcome-logged predictions to report audited accuracy and savings. Plant manager and leadership views mature; first physical retrofit shortlist executed at a scheduled maintenance window.

Phase 4 · Year 2
Generalise across sites

Re-platform the station-tier model for a second line/site with different layout and sensor maturity, using Phase 3's audited case to justify the expansion without re-litigating the core mechanism.

6Risks & Mitigations

Named directly, mitigated by design

RiskSeverityMitigation
False alarms erode floor-level trust faster than they build itCriticalConfidence-banded predictions (2.1); back-testing before any model goes live (2.2); outcome log surfaced back to the floor supervisor so accuracy is visible, not asserted
Multi-causal root causes get mis-attributed to the wrong factorHighRecommendations name a ranked hypothesis with contributing signals, not a single asserted cause — framed for human judgement, not automated diagnosis
Model tuned to one line's data doesn't transfer to another siteHighStation-tier modelling (2.1) is layout-agnostic by construction; Phase 4 is scoped explicitly to test and correct this before wider rollout
Camera or sensor data quality degrades (lighting, occlusion, wear) without anyone noticingMediumContinuous signal-quality monitoring per station; a station whose input quality drops is flagged as low-confidence automatically, never silently trusted
Scope creep toward a full physics-accurate twinMediumSection 2.1's explicit modelled-vs-inferred boundary is a standing constraint revisited at every phase gate, matching the Round 1 discipline of modelling behaviour, not physical detail
7Working Assumptions

Stated explicitly, adapted freely

Line configuration

A mixed-model assembly line of 30–50 stations spanning body construction, paint and final assembly — consistent with the brief's reference parameters, and representative of the segment where this twin's value is highest.

Sensor coverage

A majority of stations are well-instrumented (Tier A); a meaningful minority are manual-checklist only (Tier C) at the outset. Camera-augmentable (Tier B) coverage is treated as the primary lever for narrowing that gap without a maintenance window.

Maintenance access

Physical instrumentation changes are only possible during a small number of scheduled maintenance windows per year — the entire integration approach (2.4) is designed to deliver value without depending on this constraint.

Generalisation intent

These parameters are illustrative, not a fixed dataset. The station-tier model and confidence-banding approach are designed to hold across different layouts, equipment vintages and sensor maturities — this is treated as a design requirement, not an assumption to be revisited later.
